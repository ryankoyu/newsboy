## 0. 한 줄 요약

Next.js(프론트+API) + Supabase(인증·DB·스토리지) 위에, **매일 1회 실행되는 파이프라인**이 RSS를 모아 사건별로 묶고 Top 10을 뽑아 레벨별로 재작성한 뒤, **운영자(창업자)가 웹 검수 화면에서 승인해야만** 발행되는 구조. 파이프라인은 별도 서버리스가 아니라 **Supabase에 붙은 단일 Node 워커 + 스케줄러**로 돌린다. 마이크로서비스 없음. 콘텐츠 상태는 DB의 `status` 컬럼으로 추적한다. (파이프라인 **단계** 진행 상태는 `status` 컬럼이 아니라 `pipeline_checkpoints` 테이블의 `payload`에 담긴다 — §2 참조.)

### 1.1 프론트엔드 — Next.js 가정 검증

**결론: Next.js 적합. [문서]**

- 프로젝트 확정 사항은 "웹 우선 + 반응형 웹앱, 앱은 나중"(브리핑 15장). Next.js App Router는 반응형 웹 + SEO(발행 뉴스는 검색 유입 자산) + 서버사이드 렌더링을 한 프레임워크로 처리한다.
- 레벨 전환(A2↔B1↔B2)은 서버 왕복 없이 **클라이언트에서 즉시 전환**해야 체감이 좋다 → 세 버전을 한 번에 받아 클라이언트 상태로 토글. Next.js의 서버 컴포넌트로 초기 데이터를 실어 보내고, 전환은 클라이언트에서 처리하는 패턴이 정확히 들어맞는다.
- Vercel(제작사) 호스팅과 결합 시 배포·도메인·CDN이 버튼 몇 번. 1인 운영에 유리.
- **대안 검토**: 순수 정적(HTML) → 사전·인증·동적 콘텐츠가 있어 부적합. Remix/SvelteKit → 가능하나 Supabase·Vercel 생태계 예시와 AI 에이전트의 학습 데이터가 Next.js에 가장 두텁다 `[추측]`. Next.js 유지 권장.

### 1.2 백엔드/DB — Supabase 가정 검증 (1인 비개발자 관점)

**결론: MVP는 Supabase 적합. 단, 아래 대안과 트레이드오프를 메인 에이전트가 인지하고 선택.**

| 관점 | Supabase | 대안 A: bkend.ai (BaaS) | 대안 B: 직접 Postgres+서버 |
|---|---|---|---|
| 인증(회원·레벨) | 내장 Auth | 내장 Auth·RBAC | 직접 구현 |
| DB | 관리형 Postgres | 관리형 | 직접 운영 |
| 파일(일러스트) | Storage 내장 | Storage 내장 | 직접(S3 등) |
| 1인 운영 난이도 | **낮음** (대시보드 GUI) | 낮음 | 높음 |
| 파이프라인 워커가 붙기 | 서비스 키로 직접 쓰기 쉬움 | MCP/SDK 경유 | 자유롭지만 직접 |
| 비용(초기) | 무료 티어→$25/월 Pro | 티어별 | 서버비+운영 |
| 락인 위험 | Postgres라 이전 쉬움 | 상대적으로 높음 `[추측]` | 없음 |

- 이 팀 환경엔 bkit/bkend 플러그인이 설치돼 있어 대안 A도 실현 가능하다. 다만 **핵심 판단 기준은 "1인 비개발자가 데이터를 눈으로 보고 손댈 수 있는가"** 인데, Supabase는 웹 대시보드에서 테이블을 스프레드시트처럼 직접 보고 고칠 수 있어 검수·디버깅에 유리하다 `[문서]`.
- **RLS(Row Level Security)**: 발행된(`published`) 콘텐츠만 익명 사용자가 읽게 하고, 검수 전 초안은 운영자만 보게 막는다. 파이프라인 워커는 서비스 롤 키로 우회.
- **권고**: MVP는 Supabase. 단 §6의 결정지 참고.

### 1.3 파이프라인 실행 환경

- 파이프라인은 **웹 요청 흐름과 분리된 배치 작업**이다. 사용자 트래픽과 무관하게 하루 1번, 수 분~수십 분 돌고 끝난다.
- 따라서 "상시 켜진 서버"가 아니라 **스케줄에 의해 기동되는 단발 워커**가 맞다. 실행 위치 후보는 §5에서 결정지로 제시.
- LLM 호출이 길게(재작성+재시도 루프) 이어질 수 있으므로, 짧은 함수 타임아웃(예: 서버리스 10~60초)에 갇히면 안 된다 `[문서]`. → **단계별로 쪼개 실행**하고 각 단계 결과를 커밋(중단돼도 이어서 재개 가능)하는 구조로 설계한다. (Supabase 실행에서는 실제로 DB에 커밋한다 — `pipeline_checkpoints`, §2 참조. 로컬 실행은 JSON 파일.)

## 2. 일일 콘텐츠 파이프라인 (단계별 실행·실패처리)

핵심 원칙: **각 단계는 성공 지점을 체크포인트로 남기고 끝난다.** 중단된 실행은 마지막 성공 지점부터 재개한다. 사람 승인(7단계) 없이는 절대 발행되지 않는다(브리핑·소싱전략의 공개 콘텐츠 승인 원칙).

> 📌 **2026-08-12 — 체크포인트가 러너 밖으로 나왔다(위 이탈 해소).** 이 자리에는 원래 "설계는 DB라고 썼는데 구현은 러너 로컬 JSON 파일"이라는 경고가 있었다. 그 파일 방식은 §6에서 고른 실행 환경(GitHub Actions)이 임시 러너라서, job 이 죽고 다시 dispatch 되면 체크포인트가 통째로 사라졌다 — 즉 이 절의 핵심 원칙이 정작 운영 환경에서만 성립하지 않았다.
>
> 지금은 **어디에 두느냐를 저장소 어댑터가 정한다.** Supabase 어댑터(`storage/supabase.ts`)는 `pipeline_checkpoints` 테이블에 쓴다(`supabase/migrations/0005_pipeline_checkpoints.sql` — 에디션 날짜 1행, `payload jsonb`에 `PipelineCheckpoint` 전체, RLS는 service_role 전용). LocalFile 어댑터는 `storage/checkpointFile.ts`의 JSON 파일을 그대로 쓴다 — 그 실행은 파일을 가진 바로 그 기계에서 도니까. 규칙은 하나다: **그 어댑터의 실행이 프로세스가 죽은 뒤에도 닿을 수 있는 곳에 둔다.**
>
> 남은 단서 두 가지. (a) 단계 진행을 추적하는 `status` 컬럼은 여전히 없다 — 진행 상태는 `payload` 안에 어느 단계 키가 채워졌는가로 표현된다. (b) 실제로 중단된 Actions job 을 재개해 본 기록은 아직 없다(확인 근거는 단위 테스트뿐). 현재 상태 판정은 feature-status.md §1-A "단계 체크포인트 · 중단 지점 재개" 참조.

```
소스 상태 흐름:  collected → clustered → selected → extracted →
                 rewritten → gated → REVIEW → published (or rejected)
```

### [1] RSS 수집
- 소싱전략 §1 화이트리스트(BBC·Guardian·Al Jazeera·NPR·Korea Herald·연합영문·TechCrunch·Verge·Ars 등) + Google News RSS 주제쿼리. 구현은 `pipeline/src/config/sources.ts` 의 피드 35개다 `[관찰]`.
- **GDELT 는 수집 소스가 아니다.** 이 문서의 이전 판은 GDELT 를 화이트리스트 옆에 수집원으로 적었으나, 구현은 의도적으로 그렇게 하지 않았다 — GDELT 의 기사 집합을 그대로 받으면 약관을 아무도 확인하지 않은 임의 도메인의 본문을 끌어오게 되고, 이는 이 절의 마지막 항목("크롤링·페이월 우회 금지 — RSS/공개만", 소싱전략 §1)이 금지하는 일이다. 그래서 GDELT 는 [3] Top10 선정 단계의 **Layer 2 "글로벌 영향력" 점수 신호로만** 쓴다(top10-curation.md §1 Layer 2 · `pipeline/src/pipeline/globalImpact.ts`, 근거 주석은 같은 파일 머리말). 기사 수·보도 국가 수라는 메타데이터만 읽고, GDELT 의 본문은 기사에 한 글자도 들어가지 않는다 `[관찰]`.
- **실패 처리(R3 실증: 403/타임아웃 빈발)**: 소스별 재시도(지수 백오프), 타임아웃 상한, **안정 소스 화이트리스트 우선**. 특정 소스가 죽어도 파이프라인 전체는 진행. 수집 성공한 raw를 `sources` 테이블에 저장(URL·발행시각·본문·수집상태).
- 크롤링·페이월 우회 금지(소싱전략 §1 법무 기준) — RSS/공개만.

### [2] 사건 클러스터링 (같은 사건 복수 소스 묶기)
- 같은 사건을 다룬 여러 소스를 하나의 "이벤트"로 묶는다(R3의 EVENT 단위).
- 방법: 헤드라인·본문 임베딩 유사도 + 발행 시간창으로 1차 그룹핑 → 경계 사례는 LLM로 "이 두 기사가 같은 사건인가" 판정. `[추측]` 임베딩만으로 100%는 어려워 LLM 보정 필요.
- 산출: `event` 그룹 + 각 이벤트에 속한 소스 목록.

### [3] Top 10 선정
- 기준(브리핑 5·10장): ① 세계적 중요도 ② 한국인 관심 ③ 영어 학습 적합성 + 균형 구성(World/Korea/AI·Tech/Business/Culture·Sports).
- **2소스 검증 게이트를 여기서 1차 적용**(소싱전략 §4-4): 독립 2소스 이상에서 확인된 이벤트만 후보. 미달 이벤트는 "다음 배치로 보류".
- LLM에 이벤트 요약 목록을 주고 균형까지 고려해 10개 선정. 산출: 선정된 10개 이벤트.

### [4] 사실(Fact) 추출
- 이벤트별로 소스 본문에서 사실만 추출 → **각 사실에 근거 소스를 태깅**(R3의 fact table 구조: 사실 | 확인 소스 목록 | 단일/복수).
- 규칙(소싱전략 §2): 2소스 일치 사실 우선, 단일 소스 세부는 제외/완화, 직접 인용은 원문 그대로 검증 안 되면 삭제.
- 산출: `fact_provenance` 레코드(사실 문장 ↔ 소스 매핑). §4에서 상세.

### [5] 레벨별 재작성 (A2 / B1 / B2)
- 추출된 사실만으로 **완전히 새로 작성**(소싱전략 §2-1: 방어 근거는 "표현을 새로 썼다").
- 분량 목표(브리핑 5장): A2 150~180 / B1 ~300 / B2 ~520 단어. 제목도 새로 씀.
- 산출: `article_versions` 3건(레벨별 본문·제목) + 핵심 단어·퀴즈(초안).

### [6] 품질 게이트 (자동, 불합격 시 재작성 루프)
소싱전략 §4를 그대로 구현. 하나라도 불합격이면 해당 항목 재작성 후 재검사(루프 상한 예: 3회, 초과 시 사람 검수로 보류 플래그).

- **6a. CEFR 난이도 검사**: 각 버전이 목표 레벨 밴드 안인가(R3: B2가 C1로 드리프트). 어휘 빈도 밴딩 + 문장 길이 지표로 1차 자동 검사, 애매하면 LLM 판정. 초과 시 해당 버전 재작성.
- **6b. n-gram 원문 중복 검사**: 발행 전 원문 대비 표현 중복(소싱전략 §4-2). 고유명사·불가피한 사실 표현은 예외 처리, 복제된 절이 걸리면 재작성.
- **6c. 2소스 검증 재확인**: 게재되는 각 사실이 §4의 provenance상 2소스 이상인가 최종 확인. 미달 사실은 문장에서 제거/완화.
- **6d. 단어·퀴즈 가드레일**(소싱전략 §4-5): 발음·한국어 뜻은 사전 소스로 검증(빈칸 채우려 지어내는 지점).

### [7] 사람 최종 승인 (필수)
- **자동 발행 금지.** 창업자가 관리자 화면(Next.js 보호 라우트)에서 10개 기사의 A2/B1/B2·단어·퀴즈·provenance(사실→소스 링크)를 확인.
- 승인 → `status=published`. 반려 → `rejected`(사유 기록) 또는 재작성 재큐.
- 규칙 근거: 공개+창업자 명의 콘텐츠는 등록 전 최종 승인(개인 작업규칙 3장·규칙4, 소싱전략).

### [8] 발행
- `published`로 바뀐 시점부터 홈/기사뷰어가 노출. 하단에 참고 원문 URL 복수 링크(Breaking News English 방식, 소싱전략 §3).

### 실패·재시도 요약
| 단계 | 흔한 실패 | 처리 |
|---|---|---|
| 수집 | 403/타임아웃 | 소스별 재시도·백오프, 화이트리스트 우선, 부분 성공 허용 |
| 클러스터/선정 | 소스 충돌·부족 | 전문>요약 우선, 2소스 미달 보류 |

## 3. LLM 활용 설계

### 3.1 단계별 모델급 배분

원칙: **판단·글쓰기 품질이 중요한 단계는 상위 모델, 대량·기계적 단계는 하위 모델.** `[문서]` 가격은 아래 3.3.

| 단계 | 작업 성격 | 권장 모델급 | 근거 |
|---|---|---|---|
| [2] 클러스터 경계판정 | 짧은 이진 판단(다건) | Haiku급 | 저렴·빠름, 임베딩이 1차 처리 |
| [3] Top10 선정 | 종합 판단(1회/일) | Sonnet급 | 균형·중요도 판단, 호출 적음 |
| [4] 사실 추출 | 정확성 중요 | Sonnet급 | provenance 정확도가 핵심 |
| [5] 재작성 A2/B1/B2 | **품질 최상** | **Opus급** | 서비스 핵심 자산, 레벨 정합·문장맛 |
| [6a] CEFR 판정(보정) | 짧은 판단 | Haiku급 | 지표가 1차, LLM은 보조 |
| [6] 단어·퀴즈 생성 | 구조적 생성 | Sonnet급 | 정확도 필요, 사전으로 검증 |

> 재작성이 최대 비용·최대 가치 지점. 여기만 Opus, 나머지는 Sonnet/Haiku로 눌러 비용을 관리한다.

### 3.2 프롬프트 단계 구성

- **역할 분리**: "사실 추출 프롬프트"와 "레벨별 재작성 프롬프트"를 분리(추출이 오염되면 재작성도 오염). R3에서 이미 이 순서로 실증됨.
- **provenance 강제**: 추출 프롬프트가 사실마다 `[소스: URL, 단일/복수]` 태그를 반드시 붙이도록 스키마 고정(구조화 출력).
- **레벨 밴드 명시**: 재작성 프롬프트에 목표 단어수·문장길이·금지어(상위 밴드 어휘)를 명시. 게이트 불합격 시 "어느 지표가 초과했는지"를 다음 프롬프트에 피드백해 재작성.
- **인용 규칙**: 직접 인용은 소스에서 원문 그대로 검증된 것만, 아니면 삭제(소싱전략 §2-4).
- **가드레일 문구**: "원문에 없는 사실·수치·인용을 지어내지 말 것"을 시스템 프롬프트에 명시(개인 작업규칙 3장 재발방지).
- 프롬프트 캐싱: 시스템 프롬프트·공통 지침은 고정 접두로 캐싱해 비용 절감 `[문서]`.

### 3.3 월 비용 추정 (근거 있는 대략치 — 추정임을 명시)

> **[추측] 전제**: 하루 10기사 × (사실추출 + A2·B1·B2 재작성 + 단어·퀴즈) + 선정·클러스터. 실제 토큰은 소스 길이·재시도 횟수에 좌우되므로 **±2배 오차 가능**. 아래는 규모 감을 잡기 위한 값이며 실측 전 확정 금지.

가격(현재, 1M 토큰당) `[문서]`: Opus급 입력 $5 / 출력 $25 · Sonnet급 입력 $3 / 출력 $15 · Haiku급 입력 $1 / 출력 $5.

**하루치 대략 토큰 가정**
- 재작성(Opus): 기사당 입력 ~8K(소스 본문+지침), 출력 ~2.5K(3레벨 합). 10기사 → 입력 80K·출력 25K.
  - = 80K×$5/1M + 25K×$25/1M = $0.40 + $0.625 ≈ **$1.03/일**
- 사실추출+선정(Sonnet): 입력 ~120K, 출력 ~20K.
  - = 120K×$3/1M + 20K×$15/1M = $0.36 + $0.30 ≈ **$0.66/일**
- 단어·퀴즈(Sonnet): 입력 ~30K, 출력 ~15K ≈ $0.09 + $0.225 ≈ **$0.32/일**
- 클러스터·CEFR보정(Haiku)+재시도 여유: ≈ **$0.30/일**

**합계 ≈ $2.3/일 → 월 약 $70.** 재시도 루프·소스 증가를 감안한 안전 상한을 잡으면 **월 $100~150 선** `[추측]`. 임베딩(클러스터용)은 별도지만 소액. TTS는 MVP 범위 밖(V1.5).

> 결론: MVP 파이프라인 LLM 비용은 **월 100달러 안팎**으로, 1인 창업 부담 범위. 재작성만 Opus로 눌러둔 게 비용 통제의 핵심.

## 4. Provenance (사실→소스 추적) 메타데이터

**목적**: 게시된 모든 문장의 근거를 감사(audit)할 수 있게 유지(소싱전략 §2-5, 개인 작업규칙 3장 재발방지). 이 시스템이 "지어내지 않았다"를 증명하는 뼈대다.

### 4.1 어디에 저장되나
- DB 테이블 `fact_provenance` (상세 스키마는 A2). 개념 필드:
  - `fact_id` · `event_id` · `fact_text`(추출된 사실 문장) · `source_ids`(확인 소스 배열) · `confirmation`(단일/복수) · `used_in_versions`(어느 레벨 본문에 실렸는지) · `quote_verified`(인용이면 원문 대조 여부).
- `sources` 테이블: 각 소스의 URL·매체·발행시각·수집상태·(가능시)본문 스냅샷.
- 파이프라인 [4]단계에서 생성되어 [6c] 게이트가 이걸 검사하고, [7] 검수 화면이 이걸 렌더링한다.

### 4.2 어디에 노출되나
- **운영자 검수 화면(내부)**: 각 문장 옆에 근거 소스 링크·단일/복수 배지 표시 → 창업자가 "이 사실 2소스인가"를 눈으로 확인하고 승인. 이게 §2 [7]단계의 핵심 UI.
- **사용자 화면(외부)**: 기사 하단에 참고 원문 URL 복수 링크(Breaking News English 방식). 문장 단위 소스까지 사용자에게 노출할지는 제품 결정 `[추측]` — MVP는 "하단 출처 목록"으로 충분하고, 문장별 노출은 나중 옵션.
- 감사 요청 시 `fact_id`로 특정 문장의 근거를 되짚을 수 있어야 한다.

## 5. 배포·운영

### 5.1 호스팅
- **프론트+API**: Vercel(Next.js) — 배포·CDN·프리뷰 자동. 1인 운영 적합.
- **백엔드/DB/Auth/Storage**: Supabase 관리형.
- **파이프라인 워커**: 아래 §6 결정지 참고(GitHub Actions 스케줄 vs Supabase 스케줄 함수 vs 소형 상시 워커). 어느 쪽이든 **하루 1회 기동 → DB에 상태 남기고 종료** 원칙은 동일.

### 5.2 도메인
- 커스텀 도메인 1개(예: briefly.xxx) → Vercel에 연결(DNS 몇 줄). 서비스명은 가칭 BRIEFLY, 네이밍 확정 후 교체 가능하도록 환경변수화.

### 5.3 모니터링 (최소 구성)
- 파이프라인 실행 결과를 **DB `pipeline_runs` 테이블**에 1행씩 기록(시작·종료·단계별 성공/실패·처리 기사 수·비용 추정).
- 실패 시 알림: 파이프라인이 끝에서 창업자에게 이메일/슬랙 1건(성공/실패·검수 대기 N건). `[추측]` 무료 이메일 API 또는 카카오/슬랙 웹훅.
- 프론트 오류·업타임: Vercel 기본 로그 + (선택) 무료 티어 에러 트래킹. MVP는 과하게 붙이지 않는다.
- LLM 비용 관측: 각 파이프라인 실행의 토큰/비용을 `pipeline_runs`에 누적 → 월 비용이 예상을 넘으면 조기 감지.

## 6. 메인 에이전트가 결정해야 할 선택지

1. **파이프라인 실행 환경** (권장: A)
   - A) **GitHub Actions 스케줄** — cron으로 하루 1회 Node 워커 실행. 무료(공개/사적 한도 내)·설정 단순·로그 자동. 긴 LLM 루프도 넉넉한 타임아웃. **1인 운영 최적 `[추측]`.**
   - B) Supabase 예약 함수(pg_cron/Edge) — DB 근접이나 긴 배치엔 타임아웃 제약 `[문서]`.
   - C) 소형 상시 워커(Fly/Railway) — 유연하나 상시 비용·운영 부담.
   - → **A 권장**, 단계별 커밋으로 재개 가능하게.
   - ⚠️ **2026-08-12 실측**: A를 골랐고 실제로 그 위에서 돈다. 한동안 재개 체크포인트가 러너의 로컬 파일이어서 **job 이 죽고 다시 dispatch 되면 처음부터 돌았다** — A를 고른 근거였던 "단계별 커밋으로 재개 가능하게"가 정작 A에서만 깨져 있었다. 같은 날 체크포인트를 `pipeline_checkpoints` 테이블로 옮겨 해소했다(§2). 다만 실제로 중단된 job 을 재개해 본 기록은 아직 없다.

2. **백엔드**: Supabase(권장) vs bkend.ai. 둘 다 1인 운영 가능. Supabase는 대시보드로 데이터를 직접 보고 고치기 쉬워 **검수·디버깅 우위**. 팀에 bkend 플러그인이 있으니 강한 락인 회피를 원하면 재검토 가능 — 다만 MVP는 Supabase 권장.

3. **재작성 모델급 고정 여부**: 재작성=Opus 권장(핵심 품질). 비용을 더 눌러야 하면 B1/B2만 Opus, A2는 Sonnet 등 혼합 실험 가능 — **실측 후 결정**(현재 비용은 추정).

4. **문장별 provenance의 사용자 노출 범위**: MVP는 "기사 하단 출처 목록"만. 문장 클릭 시 근거 소스까지 보여줄지는 제품 결정으로 남김.
